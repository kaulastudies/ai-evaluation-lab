# Technology roadmap: coding-agent release verification

Proposed roadmap, 30 October 2026. **AI Evaluation Lab** is the venture; **ProofGate** is the existing coding-agent demonstration. This document turns the next commercial hypothesis into bounded engineering milestones. It does not claim that customer installation, authenticated connectors, execution isolation, paid deployment or recurring revenue already exist.

Dates are relative to an approved, funded start with actual founder availability. The first 90-day targets are **15 buyer interviews, three assisted staging installs and one signed paid scope or budget-authorized LOI**. The operating scenario starts paid delivery in **month 4**, recurring service in **month 6**, and a conditional engineer in **month 7**. The current request is **$12,000 for initial validation**; follow-on amounts are unpriced. The $100,000 stress envelope is not an upfront ask. Month-4 onward work needs separately justified funding and available cash; targets and calendars do not override failed gates. See [INVESTMENT_CASE.md](INVESTMENT_CASE.md).

## Starting point and intended product

The existing public evidence provides five RARB repository tasks, 52 retained model attempts, qualified controls and replay. ProofGate demonstrates an inspectable mismatch between public tests and a frozen task contract. The separate 12-control support/approval example is offline synthetic work; it is not a customer connector or an extra 12 live-model attempts. See [EVIDENCE_LEDGER.md](EVIDENCE_LEDGER.md) and [DEMO.md](DEMO.md).

The first buyer is an engineering lead at a SaaS/software company or coding-agent integrator. The first paid scope is one repository task family and one release decision. The intended product preserves the requirement, candidate artifact, verifier version, observed result, uncertainty and reproduction path. Its value must be measured against that buyer's normal tests and review process, including installation and maintenance effort.

The product roadmap belongs to the proposal workstream. This document makes no changes to the core Lab, frozen evidence or existing scientific results. New implementation would require review in the appropriate product scope and must preserve the public/private provenance boundary.

### Execution isolation is an unbuilt dependency

The current local runner uses limited admission checks and temporary workspaces; that is not an OS security sandbox. An agreed pilot execution design must establish and test, within its stated scope:

- disposable isolated workers with an explicitly chosen OS/VM/container trust boundary; a container alone is not evidence that the boundary is secure;
- unprivileged execution, no unnecessary host mounts, no access to production credentials, and scoped read-only inputs where feasible;
- separate candidate and verifier environments, with authoritative test criteria and final verdict outside candidate write access;
- restricted outbound networking, execution time, memory/CPU, process, disk and output limits; all resource failures recorded without automatic pass;
- safe cleanup and a check for cross-run state leakage; logs and reports must not expose credentials or private repository content;
- pinned dependencies and an agreed patching process; actual review of applicable open security findings rather than assuming a proposal branch inherits unmerged fixes.

Acceptance requires executed cases for network denial, host-path access, resource exhaustion, verifier/artifact tampering, cross-run leakage, cancellation and cleanup, plus review of every unresolved finding in the agreed boundary. Preserve observed failures and retest after fixes. These controls are an engineering gate, not a general security certification. If the boundary cannot be established within budget, limit demonstrations to trusted synthetic artifacts and defer customer execution.

The proposed coding pilot has **at least 30 held-out cases**, separate from any development cases: ten valid outcomes, ten known critical violations and ten missing/inconsistent-evidence cases. The buyer and independent reviewer must agree the case construction, labels and targets before lock. If they select a larger set, preregister group sizes and thresholds before outcomes are seen. The minimum-set gates are:

- **10/10 known critical violations receive FAIL and 0/10 receive PASS**; HOLD is not successful detection. Together with at least 9/10 valid outcomes passed, this requires at least 19/20 decisive outcomes in the valid/violation partition.
- **At least 9/10 valid outcomes receive PASS**; separately count every false block, hold and error.
- **10/10 missing/inconsistent-evidence cases receive HOLD/REVIEW**, with a reason and the missing evidence identified.
- **At least 20% lower median active human review time** on matched cases versus the buyer's current process, subject to buyer agreement; retain raw paired times and control ordering/learning effects. Include time spent resolving holds, investigating failures and reviewing errors. Report setup cost separately and report end-to-end elapsed time so work is not merely shifted out of view.
- **100% same-verdict replay** on the delivered holdouts given identical pinned inputs, verifier and environment, with exact matching/attempted counts.

These are proposed continuation targets, not achieved results, generalized accuracy claims or official programme rules. Correct uncertainty handling takes priority over speed: never drop slow cases or convert a hold to a pass to meet the time target. Report any miss and rescope or stop before scaling. These small designed samples do not estimate a production incident rate or prove broad safety. The separate support/approval extension's 60-case protocol is not the first coding pilot; see [PILOT_PROTOCOL.md](PILOT_PROTOCOL.md).

The $5,000 pilot assumes 60 delivery hours, $500 external review and $250 compute. The $1,000 recurring service assumes eight delivery hours plus $100 compute. A harder task family, adapter or isolation requirement must be rescoped rather than hidden in those prices. Neither price nor the available reviewer capacity has been validated. See [FINANCIAL_PLAN.md](FINANCIAL_PLAN.md).

The engineer in the base model begins in month 7 only if funded demand, hiring route and all-in cost support it. That role is not filled or committed. Before it exists, the founder must scope work to confirmed capacity; the model's 160 hours/month is not proof of availability.

A later beta may use the 20-organization design in [PLATFORM_STRATEGY.md](PLATFORM_STRATEGY.md): record all installation attempts, repeat-release opportunities and assistance time. That is a separate post-validation experiment, not an extra first-90-day promise. Hosted multi-tenant service, authenticated cross-system connectors, Arabic-English evaluation and additional sectors each need their own demand, reviewer, security and capacity gate.

## Evidence and change control

Every milestone review should retain the version, scope, responsible human role, input/source identities, planned versus executed work, outcomes, errors, unresolved findings, actual cost, and the decision to continue, rescope or stop. Private buyer artifacts stay in an authorized private workspace. Only original synthetic or separately approved material enters the public Lab.

Hash agreement is evidence of byte consistency against a trusted reference, not proof that a remote event occurred. A model's success claim is not the verifier decision. A signed scope is not collected cash. An AI-assisted review is not independent human review. Changes to metrics, task contracts or holdouts after inspecting outcomes require a new version and explicit explanation.
