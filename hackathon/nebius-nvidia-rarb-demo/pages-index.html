Set up

Two files and
every pull request is checked.

ProofGate runs as a GitHub Action. It needs no account, API key or model call, and it uses the Python already on GitHub’s runners.

  1. Commit the rules to your main branch

    A contract lists your public tests and the requirements your verifier checks. Keep it and the verifier in a folder such as .proofgate/.

  2. Add the workflow

    Paste this file into .github/workflows/. On every pull request, ProofGate reads the rules from main, never from the pull request.

  3. Read the verdict on the pull request

    One comment per pull request, updated on each push: verified pass, false-green, fail or hold. The full evidence record is saved with the run.

How ProofGate decides

Make the verdict
worth trusting.

We start with a bounded task, test the verifier itself, and retain the evidence behind the result.

Step 1: Define

Write the contract.

Make success and failure explicit before the run. Specify the inputs, constraints and behaviour the task actually requires.

Step 2: Challenge

Check the checker.

Use reference implementations, known-bad candidates and deliberate mutations to test whether a verifier catches the faults it should.

Step 3: Reproduce

Keep the evidence.

Retain the code, failed checks, source references and execution reports. Make the result available for inspection and replay.

Roadmap

Where ProofGate
is going.

What exists today is public and runnable. What comes next is stated as a plan, not a claim.

  1. Live now

    Browser verification demo

    Recorded agent patches, independent Python checks, repair comparison and six verifier controls, running in the browser with no account.

  2. Beta now

    ProofGate on pull requests

    Add one workflow file and every pull request gets a verdict: verified pass, false-green, fail or hold. The verifier is read from the base branch, so a PR can’t rewrite its own rules.
